# Project Requests User Guide

How to raise a project request and get it approved.

---

## 1. The path a request takes

```
You create it  →  Project Manager  →  Development  →  Done
                        |
                        +→  Escalated to someone specific  →  Development
```

**Creating a project raises the request.** There is no separate Submit step, it goes to the Project Manager straight away.

Most requests need only that one approval. If yours needs someone else's sign-off, budget or another team's commitment, the Project Manager escalates it to that person by name and their approval releases it.

Anyone who can decide on a request can also decline it. The Project Manager can send one back to you for changes, which is not a rejection, just "needs work first."

---

## 2. Where things live

Open **Projects → Requests**. Five tabs:

| Tab                      | What it holds                     |
| ------------------------ | --------------------------------- |
| **All Requests**         | Everything in the workflow        |
| **My Requests**          | Requests you raised               |
| **My Pending Approvals** | Waiting on _you_, your to-do list |
| **Completed**            | Delivered                         |
| **Rejected**             | Declined                          |

**My Pending Approvals** only ever shows things you can actually act on. If it is empty, nothing needs you.

---

## 3. Raising a request

1. **Projects → New Project**, fill in the details.
2. Set a priority, approvers see it in their email, and it is how they triage.
3. Add attachments and any context in the comments while it is still a draft.
4. Click **Submit**.

It goes to the Project Manager and everyone holding that role is emailed.

**Once submitted you cannot edit it.** Approvers need to review something stable. If you need to change it, ask the Project Manager to return it, that puts it back in Draft, editable, with your history intact.

Write the description for someone who has not been in your meetings. "Integrate the wallet feed so finance stops reconciling by hand, needed before the Q4 close" gets a faster decision than "Wallet integration."

---

## 4. Approving or declining

From either the queue or the request itself:

- **Approve**, one click. Moves to the next stage immediately.
- **Reject**, click Reject, type why, confirm. Two clicks.
- **Return for changes** _(Project Manager)_, sends it back to the requester with a note.

Rejecting and returning both require a written reason of at least five characters. That is deliberate: the reason is the only thing the requester has to work with, and it becomes part of the permanent record.

"Not this quarter, resubmit in October with the revised cost" is useful. "No" is not.

### From your email

Approval emails include an **Approve** button that works without signing in, when your administrator has enabled it. Rejection always opens the app, because it needs a reason.

If the button says the link is no longer valid, someone already acted on it, or it moved past your stage. Open the request to see the current state.

---

## 5. Reading a request

Everything is on one screen:

- **Details**, what is being asked for, by whom, priority, target date
- **Attachments**, supporting files
- **Comments**, the discussion
- **Approval History**, every step, who took it, when, and what they said
- **Timeline**, the same history as a visual progress track

Approval History is the honest record. Every approval, rejection, return and reopen is there with its author and reason, and nothing can be edited or removed after the fact.

## 6. Status meanings

| Status                     | Means                                                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Draft**                  | Yours. Not submitted, still editable.                                                                                   |
| **Pending PM Approval**    | With the Project Manager.                                                                                               |
| **Escalated for Approval** | The Project Manager referred it to a specific person.                                                                   |
| **Approved**               | Fully approved. The board is unblocked and work can start. Most requests finish here; marking one complete is optional. |
| **Completed**              | Delivered. Final.                                                                                                       |
| **Rejected**               | Declined. The reason is in the history.                                                                                 |

---

## 7. Questions people ask

**Can I edit after submitting?** No. Ask the Project Manager to return it, you get it back as a Draft with the history preserved.

**My rejected request should go ahead after all.** The Project Manager can reopen it, which puts it back to Draft. You do not need to start over.

**How do I chase an approval?** The request shows which stage it is at. Add a comment, the people at that stage will see it. Nudging outside the tool loses the trail.

**Why can't I approve my own request?** Approvals belong to the Project Manager, or to whoever they escalate to. The point is that someone other than the requester looks at it. For the same reason a Project Manager cannot approve an escalation they themselves raised.

**Nothing is in My Pending Approvals but I was told to approve something.** You may not hold that stage's permission. Ask your administrator.

**I got an approval email for something unrelated to me.** If nobody holds a stage's permission, notifications fall back to administrators so requests do not stall silently. Tell your administrator, the roles likely need setting up.
