The framing fact

The database is already on AWS. Supabase runs on AWS, and the production connection strings point at *.pooler.supabase.com in an aws-*-ap-southeast-* region. The production data plane is not moving clouds — it is only moving vendor, and only if you decide it should.

What is actually on GCP is compact: two Cloud Run services, one Artifact Registry repository, some Cloud Scheduler jobs, Workload Identity Federation for CI, and the custom domain mappings. Nothing in the application code is GCP-coupled — there are no @google-cloud/* imports and no metadata-server calls.

So the large, risky parts of this migration are the Supabase question (§6) and the Socket.IO question (§9). Not the containers.

Codebase

A single-tenant internal business platform: HR/HRMS, payroll, leave, attendance, visa, Thai statutory accounting including a fixed-asset register, expenses, travel, cash advance, five CRMs, investor relations, IT operations and helpdesk, appraisals, a document knowledge base, real-time messaging, and an AI assistant (ARIA).

One deployable web app plus one deployable API. No microservices, no message queues, no worker fleet — scheduled work is HTTP endpoints invoked by a cron scheduler.

Request path, and why it matters

The browser talks only to the web origin. next.config.ts rewrites /api/:path* to the API server-side, and /ingest/* to PostHog. Auth rides httpOnly cookies the API sets itself (nexora_access_token / nexora_refresh_token) — apps/web has zero @supabase/* imports.

One exception, and it is load-bearing

NEXT_PUBLIC_SOCKET_URL is unset in prod, so the web build falls back to the API_URL build arg and the browser opens the WebSocket directly at the API hostname. A private-only API breaks messaging even though every REST call would still work through the Next.js rewrite.

Two things a schema dump will not tell you

Fails silently · pgvector

aria_knowledge_articles.embedding vector(768) and its ivfflat cosine index exist only in raw migration SQL and are absent from the Prisma schema — ARIA reads the column through $queryRaw. A target Postgres without the vector extension will boot, serve traffic, and quietly degrade ARIA retrieval to keyword overlap. Same story for the two GIN indexes on projects.departments and investors.tags, which prisma db push has never created — staging has never had them.

Confirm intent · Row-Level Security is not a tenancy model

0000_init names 94 tables, each getting exactly one policy, service_role_full_access, gated on public.is_service_role(), plus a blanket revoke of anon and authenticated. The Express API is the sole database client and authorises in application code. Two drifts: three of those 94 tables no longer exist (survey_definitions, survey_waves, upload_jobs), so the live count is 91; and the 183 tables added since have no policy at all. They stay unreachable by anon/authenticated thanks to the revokes, so it is a defence-in-depth gap, not an exposure.

The Supabase surface

The single biggest decision, because "Supabase" is doing three unrelated jobs and each has a different exit cost. They can be decided separately, and staged.

PostgreSQL — the primary datastore

Prisma connects through two URLs: DATABASE_URL (shared pooler, port 6543, ?pgbouncer=true, transaction mode) and DIRECT_URL (port 5432, session mode). Migrations run against the direct URL; the app runs against the pooled one. Any replacement must preserve that split — PgBouncer transaction mode cannot run DDL or prepared statements.

Confirm live · region disagreement

.env.example (a dev project) shows aws-1-ap-southeast-2; CLAUDE.md states aws-1-ap-southeast-1 for prod. Read the actual prod DATABASE_URL secret and settle it.

Auth — small, and entirely server-side

Nine call sites, all in apps/api, none in the frontend: signInWithPassword, signInWithOtp, resetPasswordForEmail, refreshSession, getUser, and the four admin calls (createUser, updateUserById, deleteUser, listUsers). Because the browser only ever sees the API's own cookies, the identity provider is swappable without touching a line of frontend code.

The real cost is the user migration

users.id is the Supabase auth.users.id UUID, and 202 tables reference users. Cognito will not accept an arbitrary sub, so either keep public.users.id as the canonical key and store the Cognito sub alongside it, or accept an ID remap across 202 foreign keys. The first is the only sane option. Separately, password hashes cannot be exported in a form Cognito accepts — that means a forced reset for everyone, or a Cognito migration-Lambda trigger validating against Supabase during a grace window.

Data protection

The database holds employee PII and payroll data across four jurisdictions (Thailand, India, Vietnam, Indonesia — the entities dimension). In users alone: date_of_birth, passport_number, thai_id, tax_id, aadhaar_number, pan_card_number, salary, permit_number — plus tables for payslips, ESOP grants, visa records, benefits and appraisals. Region choice on the target is therefore a compliance question, not a latency one.

What actually changes in the repository

Small, and confined to the pipeline. No application code changes are required for the compute move.

  • Both deploy workflows — auth action, push target, deploy command, and the four scheduler-provisioning steps.
  • Dockerfiles: unchanged in substance. Keep qpdf and openssl in both stages of the API image, and keep the @swc/helpers workaround in the web image — Next 16 traces only the CJS build and the container dies at boot without it.
  • .env.example: drop the vestigial GCS_BUCKET / GCP_PROJECT_ID.
  • next.config.ts: only if storage moves.
Fails silently · trust proxy

app.set("trust proxy", 1) assumes exactly one proxy hop. ALB alone is still one hop, so 1 stays correct. ALB behind CloudFront is two — leaving it at 1 makes req.ip resolve to the CloudFront edge, which mis-buckets both rate limiters (login at 30 per 15 min, everything else at 2,000) and pollutes sessions.ip_address.

Three decisions

1 · How far to unbundle Supabase

Lowest risk

A · Keep Supabase entirely

Zero data, auth or storage migration. The project reduces to moving two containers and a scheduler. Cost: a non-AWS vendor stays in the critical path.

Most hidden work

B · Postgres to RDS, keep Auth + Storage

pgvector must exist on the target with the ivfflat opclass. The pooler split must be reproduced — RDS Proxy for the pooled URL, the instance endpoint for migrations; point both at the pooled one and migrate deploy fails on DDL. The RLS layer becomes inert; decide deliberately rather than porting it by accident.

Touches every user

C · Full exit to RDS + Cognito + S3

Everything in B, plus the user migration and the password-hash problem, plus rewriting every stored fileUrl. If this is the destination, stage it: compute → storage → Postgres → Auth last. Each step is independently reversible.

2 · Fargate, App Runner, or EKS

OptionFits becauseWatch out for
ECS Fargate + ALB
default recommendation		 Closest operational analogue to Cloud Run; full control over WebSockets, stickiness, health checks, autoscaling No scale-to-zero — a warm task runs 24/7
App Runner Closest developer experience to Cloud Run; managed HTTPS and autoscaling Verify WebSocket support before choosing it. The /messages namespace is a hard requirement, and this is the one question that can disqualify the option outright
EKS If there is already a cluster and a platform team Large operational surface for two containers

Regardless: /health already exists and is the natural ALB target-group check for the API; the web service's / is a redirect, so pick a concrete page rather than health-checking a 3xx. Current sizing is 512Mi / 1 vCPU, but the API buffers uploads in memory (up to 50 MB) and shells out to qpdf — right-size from real metrics, not from the present flags.

3 · Socket.IO fan-out — a real bug, currently masked

messages.bus.ts is an in-process emitter, a Map<channelId, Set<handler>>. No Redis adapter, no shared pub/sub. Cloud Run already runs up to 10 instances, so a message sent through instance A never reaches a subscriber on instance B. This is pre-existing, not introduced by the migration — but the migration forces the call:

  • Fix it — @socket.io/redis-adapter backed by ElastiCache for Redis/Valkey. Correct at any instance count; adds a cache cluster.
  • Pin the API to one task — cheapest, honest, a documented ceiling.
  • Sticky sessions alone — insufficient. Stickiness keeps one client on one instance; it does nothing about two clients in the same channel landing on different ones.

Either way the ALB target group needs its idle timeout raised above Socket.IO's ping interval, and the API must stay publicly reachable over HTTPS.

Cutover checklist

Ordered, because it is a sequence. Every item is here because skipping it fails silently rather than loudly.

Before anything

  • Archive the real Cloud Scheduler job list — the repo documents 4 of 20 and its ops doc has drifted by three entries.
  • Read the prod DATABASE_URL secret and record the actual Supabase region; repo sources disagree.
  • Enumerate live Cloud Run domain mappings, and any Firebase Hosting site (manut.xyz is referenced in CLAUDE.md).
  • Confirm whether the Bank of Thailand FX client ID is IP-allowlisted.
  • Decide the fate of bnii-analytics-api — a separate Cloud Run service in its own repo.
  • Capture 30 days of request-count, p95-latency and memory metrics so Fargate sizing and cost are computed, not guessed.

Schema

  • Apply 03-schema.sql, then 04-schema-addendum.sql. A database built from the Prisma schema alone boots fine and quietly breaks ARIA retrieval.
  • SELECT extname FROM pg_extension includes vector.
  • aria_knowledge_articles_embedding_idx exists and is an ivfflat index.
  • projects_departments_idx and investors_tags_gin_idx exist.
  • SELECT count(*) FROM pg_policies WHERE schemaname='public' returns 91.
  • Run prisma migrate resolve --applied 0000_init on a restored database so history is not re-attempted.

Pipeline

  • GitHub OIDC → IAM role, replacing WIF.
  • All 38 prod secrets and 7 staging secrets re-homed — ideally into Secrets Manager, not plain task env vars.
  • All 3 GitHub variables preserved, including both fail-closed gates, with all three edit points wired.
  • GOOGLE_OAUTH_REDIRECT_URI re-registered for the new API hostname.
  • All 20 scheduler jobs re-created with the X-Cron-Secret header intact — and exactly one of /crm-deadline-reminders and its legacy alias.
  • Decide whether the paused marketing-drift-check goes live.
  • prisma migrate deploy still runs against the session-mode URL, before the image build, aborting the deploy on failure — and keep the migrate resolve --rolled-back … || true step.

After

  • POST /api/aria/chat still streams — compression is explicitly bypassed for that route, and a buffering ALB or CloudFront undoes it.
  • The Socket.IO handshake succeeds from the production web origin.
  • A private-bucket download returns a short-lived signed URL, not a raw object URL.
  • A payslip PDF still generates — that path shells out to qpdf.
  • /health returns 200 through the ALB, and rate-limit buckets see real client IPs rather than the proxy's.

Open questions

  1. Is Supabase in scope, or is this a compute-only migration? Everything else follows from this.
  2. If Postgres moves: RDS or Aurora, and which engine version — the answer has to satisfy pgvector with the ivfflat opclass.
  3. Fargate, App Runner, or an existing EKS cluster? If App Runner, WebSocket support has to be confirmed first.
  4. What downtime window is acceptable for the database cut? That decides pg_dump/restore versus DMS.
  5. Does messaging need to scale horizontally, or is a single API task an acceptable documented ceiling?
  6. Which region? The data sits in AWS Singapore today and holds Thai, Indian, Vietnamese and Indonesian employee PII including Aadhaar and PAN numbers.
  7. Is bnii-analytics-api migrating too, and by whom?
  8. Should DocuSign be wired up during the move, or formally retired? Nine env vars and a code path exist for an integration prod never configured.
