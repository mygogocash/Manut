# Phase 7B-0 — DataTable Responsive Hardening

**Status:** complete.
**Character:** infrastructure hardening, **not** a mass migration. 6 of 49 affected tables migrated, by a stated rule.
**No API change. No database change. No migration. No new dependency.**

## 1. Existing DataTable architecture

One component, `apps/web/src/components/shared/data-table.tsx`, 75 import sites across
73 files. It already had responsive card support from Phase 1:

| Concern | Mechanism | Phase 7B-0 |
|---|---|---|
| mode | `mobileMode: "auto" \| "table" \| "cards"` (default `auto`) | unchanged |
| breakpoint | `useIsBelow("md")` — **hardcoded 768px** | now `cardBreakpoint`, default `"md"` |
| card mapping | `mobileRole` + `deriveMobileRoles()` | `"actions"` added (Phase 7A) |
| full override | `renderMobileCard` | unchanged |
| selection | `enableRowSelection`, `selectedRowIds` | unchanged |
| sorting | `sortBy` / `sortOrder` / `onSortChange` | unchanged |
| pagination | caller-supplied node | unchanged |
| loading | `Skeleton` rows / card skeletons | unchanged |
| empty | `emptyMessage` | unchanged |
| error | **none** — DataTable has no error state; callers own it | unchanged |

Card rendering delegates to `RecordCard`, whose root is a plain `<div>`: the open-record
gesture wraps **only the heading**, the expander is its own button, and actions are a
sibling. That structure is why no `stopPropagation` is needed anywhere (§10).

## 3. The action-column problem

`deriveMobileRoles` places the first column as the title, the next two as visible fields,
and **everything else behind the expander**. It cannot distinguish an action column from a
data column, because at the type level there is nothing to distinguish — both are
`{ key, header, render }`.

An action column is almost always last, so on any table with ≥ 4 columns it lands in the
expansion. Worse, these columns overwhelmingly carry `header: ""` (so the desktop table
shows no heading), which rendered them as a card field with a **blank label**.

The concrete cost, measured in Phase 7A: an approver on a phone had to expand every row
to find Approve — one tap further away than on desktop, on the most important control in
the module.

---

## 4. Action-role API

```ts
{ key: "actions", header: "", mobileRole: "actions", render: … }
```

Added in Phase 7A; documented and hardened here. Semantics:

- the cell renders in `RecordCard`'s **action bar**, on the face of the card
- it is **not** also rendered as a labelled value, so no blank label appears
- **desktop is untouched** — the role is read only on the card path
- handlers, ordering and permission checks are the caller's, unchanged; the role moves
  *where* a cell renders and nothing else

**Opt-in.** `deriveMobileRoles` reads it only when declared, and declaring it does not set
`anyDeclared`, so the other columns keep exactly the placement the derivation already gave
them. That is what makes a migration a one-line change — and it is asserted by a test
(§11), not merely intended.

## 5. Card-breakpoint API

```tsx
<DataTable cardBreakpoint="lg" … />   // cards below 1024px
```

Type `Breakpoint` from `@/hooks/use-breakpoint` — `sm | md | lg | xl | 2xl`. One prop, no
config object, no second system.

Deliberately a **sibling** of `mobileMode` rather than folded into it, because the two
answer different questions: `mobileMode` is *whether* to switch, `cardBreakpoint` is
*where*. It has no effect on `"table"` or `"cards"`, which are absolute by definition —
tested.

### Breakpoint validation (Step 10 — verified, not assumed)

`globals.css` declares **no** custom breakpoints, so Tailwind v4 defaults apply, and
`BREAKPOINTS` in `use-breakpoint.ts` matches them exactly:

| | sm | md | lg | xl | 2xl |
|---|---|---|---|---|---|
| px | 640 | 768 | 1024 | 1280 | 1536 |

`useIsBelow(bp)` queries `max-width: BREAKPOINTS[bp] - 1`, so the boundary is
inclusive-at-the-top: at `lg`, 1023px is a card and **1024px is a table**. Both sides are
tested, and both were confirmed in a browser.

## 6. Default behaviour

`cardBreakpoint` defaults to `"md"` — the exact 768px that was hardcoded before. **Every
one of the 75 call sites renders identically to how it did before this phase**, at every
width, unless it opts in. This is the load-bearing claim of the phase and it has three
independent proofs: a unit test at 700px and 900px, a browser control table measured
alongside a migrated one at seven widths, and the pre-existing 14 desktop DataTable tests.

## 9. Touch targets

The migrated tables' controls are `size="xs"` — **24px**, written for a desktop table row.

Enforced **once**, in `RecordCard`'s action bar, rather than at 49 call sites:

```
[&_button]:min-h-11 [&_button]:min-w-11 [&_a]:min-h-11
```

`min-*` so a control already larger is untouched; the desktop **table** never renders this
element at all. Measured: 24px in the table at 834/1280/1920, 44px in the card at
320/390/430. A link stays a link and a button stays a button — nothing was converted into
a card-wide click target.

## 10. Accessibility

Three gestures can coexist on one card — open the record, expand it, act on it. They are
separated **structurally**, not with event handlers: the card root is a plain `div`, and
each gesture owns its own `<button>`. Six tests assert every pair in both directions, and
one asserts an action button's nearest `button` ancestor is itself — an
interactive-in-interactive nesting would fail it.

Also verified: `aria-expanded` on the expander, accessible names on action triggers,
`aria-label="Select row"` on card checkboxes, real `<th>` semantics preserved in table
mode.

**No automated accessibility scanner was run**, so no WCAG conformance is claimed. The
44px figure is WCAG 2.5.5 / Apple HIG measured directly.

## 15. Known limitations

1. **43 tables still bury their action column** (§8). Deliberate; each is one line.
2. **The 6 migrated tables were not exercised with a real session.** No authenticated pass
   was possible, so leave / travel / expenses / disposal / attendance / payroll cards were
   verified by unit test and by an equivalent harness table, not against live data.
3. **No accessibility scanner was run** (§10).
4. **`RecordCard`'s `row` expand mode hides actions until expanded** —
   `expandMode === "button" || expanded`. No `DataTable` path uses `row` mode, so it is
   latent, but the next adopter would reintroduce exactly the bug this phase fixed.
5. **`cardBreakpoint` is per-table, not per-column-count.** A table cannot say "cards when
   my columns exceed the width"; somebody has to choose the breakpoint.
6. **DataTable still has no error state** — callers render errors themselves, so "do not
   show empty for an API error" remains a per-caller property, unverified across 73 files.
