| Run | Conditions | Result |

### Source proof (unchanged, and now corroborated)

Manifest: `id`, `name`, `short_name`, `description`, `lang`, `dir`, `start_url`, `scope`,

**The cache cannot contain anything authenticated.** The fetch handler is a strict funnel:

| Rule | Behaviour |
|---|---|
| non-GET | returns immediately — no queue, no replay (an approval cannot be re-fired) |
| cross-origin | returns immediately — every Supabase signed URL bypasses the worker |
| `/api/`, `/auth/`, `/ingest/` | never cached, **never intercepted** |

| **navigations** | `return await fetch(request)` — **never `cache.put`**; the only cache read is the generic offline page |

consent (no unsolicited `skipWaiting`); everything is capability-guarded, so a browser without

## 29. Defects found and fixed

### FIXED — P1: the desktop sidebar started collapsed at every width

`apps/web/src/app/(dashboard)/layout.tsx`

The programme changed `<SidebarProvider defaultOpen={true}>` to `defaultOpen={isWide}`, with a
comment asserting the sidebar would *"settle open on desktop after mount"* and that above `xl` it
was *"unchanged: open by default, exactly as desktop has always behaved."*

It cannot settle. Four facts, each verified in source:

1. `useIsAtLeast("xl")` is `useState(false)` + an effect — **`false` on the first render at every
   width**.
2. `SidebarProvider` does `useState(defaultOpen)` — an **initial value**, read once.
3. The provider's only `useEffect` is the keyboard shortcut. There is no sync effect.
4. The `sidebar_state` cookie is **written but read nowhere** in the codebase.

So `open` was pinned `false`, `state = open ? "expanded" : "collapsed"` resolved to `"collapsed"`,
and with `<Sidebar collapsible="icon">` a 1920px desktop rendered the **icon rail on every page
load** — the labelled sidebar desktop has always had, gone. Directly contrary to the programme's
own "SAME desktop experience" constraint, and untested.

**Fix** — make the provider controlled, which is what delivers the documented intent:

```tsx
const [sidebarOpen, setSidebarOpen] = useState(false);
useEffect(() => setSidebarOpen(isWide), [isWide]);
…
<SidebarProvider open={sidebarOpen} onOpenChange={setSidebarOpen} …>
```

Initial `false` preserves the no-flash-on-tablet behaviour; the effect then opens it on desktop.
`SidebarProvider` already supports controlled mode and still writes the cookie, so manual toggling
is unaffected.

**Test** — `apps/web/src/app/(dashboard)/__tests__/sidebar-open-state.test.tsx`, 5 cases: two
behavioural tests pinning the React semantics (a `defaultOpen` that flips after mount is ignored;
an `open` prop that flips is tracked) and three source invariants on the layout.

**Break-tested.** Reverting the fix fails 2 of the 5. The first attempt at that break-test silently
did not apply — a CRLF mismatch — and reported a false pass; I printed a confirmation flag, caught
it, and redid it with a newline-agnostic regex.

## 34. Final recommendation

### READY TO MERGE WITH KNOWN LIMITATIONS — after a rebase

Every automated gate passes on an uncached run. The one desktop regression this phase found is
fixed and break-tested. Nothing in the change set is unsafe: no live secret, no permission
regression (1,235/1,235 and 207/207, with zero authorization lines in the diff), no destructive
migration, no cached authenticated response, no surviving debug route.

**Three things must happen before this becomes a PR:**

1. **Rebase onto `dev`.** 138 commits behind with 33 overlapping files and a guaranteed
   `Dockerfile.web` conflict is not a mergeable state.
2. **Decide on `AGENTS.md` / `CLAUDE.md`** — commit or ignore, not by accident.
3. **Write the PR description honestly.** This is not a presentation-only change: it adds a
   database table, an API module, a push capability, and three behaviour changes, and it makes two
   deliberate app-wide desktop changes (sheet widths, `--muted-foreground`) that need sign-off.

**And independently of all of it: rotate the System Admin credential.**

### READY TO MERGE is not READY FOR PRODUCTION

The code is safe to submit for review. It has still never been run by a real user against real
data. Authenticated UAT, RBAC negative testing, real push delivery, physical-device installation
and the download paths all remain unverified — and the account that would unblock them has been
outstanding for twelve phases.

The next action is **PR → CI → Dev/Staging → authenticated UAT**, not another engineering phase.
